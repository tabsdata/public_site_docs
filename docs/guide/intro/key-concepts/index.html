Key Concepts

This page explains how Tabsdata works, one idea at a time. Each concept builds on the ones before it, so you can read top to bottom and stop whenever you have enough: everything up to that point stands on its own.

Functions: how data moves​

Tabsdata moves and shapes data with small Python functions. There are three kinds:

  • Publishers bring data in: they read from an external system (a database, files, cloud storage, a messaging system) and add it to Tabsdata.
  • Transformers reshape data that is already inside Tabsdata, turning tables into new tables.
  • Subscribers send data out, from Tabsdata to an external system.

That is the whole model: publish in, transform in the middle, subscribe out.

Tables​

Data lives in tables. A table is rows and columns, each column has a name and a data type. Functions read tables and write tables.

TableFrames: working with table data​

Inside a function, you work with TableFrames: a dataframe-like structure for filtering, joining, aggregating, and reshaping table data. TableFrames are built on Polars and process data lazily, so they can handle tables larger than memory.

Collections: how tables are organized​

Related tables are grouped into a collection. A collection holds a set of tables and the functions that produce them. It is the main unit you create and work with.

The three kinds of collection​

A collection is specialized by the kind of function it holds:

  • A source collection ingests data. It holds publishers and belongs to the built-in sources group.
  • A destination collection exports data. It holds subscribers and belongs to the built-in destinations group.
  • A data product collection transforms data. It holds transformers and belongs to the default group, or to any group you create.

Connections: reaching external systems​

A source or destination collection has exactly one connection to an external system: the source it reads from, or the destination it writes to.

  • The connection's type is fixed when the collection is created: the collection always works against the same kind of system. You can update its details (host, port, credentials), but you cannot switch it to a different type of connection (for example, from S3 to MySQL).
  • All publishers in a source collection share its one connection. The same is true for all subscribers in a destination collection.

See Connections for how to build one.

Groups: organizing collections​

Collections are organized into groups. sources and destinations are built in. Every source and destination collection lives there and cannot move.

For data product collections you can use the default group, or you create your own groups. For example, to set up a medallion architecture you would create bronze, silver, and gold groups and place your data product collections in them. Data product collections are the only ones that can move from one group to another.

Storage: where table data lives​

Before and after every function runs, Tabsdata keeps the table data in its configured storage. This can be local disk or cloud storage. You never manage files by hand. Tabsdata reads and writes table versions there for you.

Versions: nothing is ever overwritten​

Existing data is immutable. A function never changes a table in place. Every run creates a new version of the table.

  • A new version can be an incremental change: just the rows added or changed since the last version, a delta (the common case), or a full snapshot that replaces the table's contents. Either way, earlier versions are never touched.
  • Each version's schema can differ from the previous one: columns can be added, removed, or retyped.
  • Every previous version stays accessible. That gives you time travel: read a table as it was at any point. And because a function can read several versions of the same table at once, it also enables cross-time queries spanning multiple versions.

Data dependencies​

Every function declares the tables it reads and the tables it writes:

  • A publisher writes output tables, built from external data.
  • A transformer reads input tables and writes new output tables.
  • A subscriber reads input tables and sends them out.

A transformer can read tables from its own collection or from other collections, referenced as collection/table. These read/write links connect functions into a dependency graph: one function's output table is another function's input.

Triggers​

A trigger decides when a function runs. There are three ways:

  • Manually: you run it yourself (for example, tdk fn trigger). This is the default for publishers.
  • On a schedule: a cron schedule fires the function at set times.
  • On new data: the function fires automatically whenever an upstream table it depends on gets a new version. You can watch every table it reads, or just a specific set.

Execution plans​

No matter which trigger fires a function, Tabsdata does not run just that one function. It follows the data dependencies and automatically builds an execution plan: the graph of every function that must run as a result, in the correct order, across collections.

For example, trigger a publisher and Tabsdata runs it, then every transformer that reads its output, then every subscriber downstream, with no orchestration to wire up yourself. You never build or maintain this graph; Tabsdata generates it from the dependencies each time.

Execution plans are 100% deterministic: both the graph Tabsdata builds and the exact table versions each function reads and writes are fixed and recorded up front. The same starting point always produces the same plan over the same data.

Transactions: all-or-nothing changes​

Changes are transactional per collection. Because an execution plan can span several collections, it is multi-transactional: each collection it touches commits as its own transaction. Within a collection, all the tables the plan changes are committed atomically: all together, or not at all. You never see a half-updated collection.

Streaming publishers​

A normal publisher pulls a batch of data each time it runs. A streaming publisher stays running continuously, creating new table versions as data arrives: for change-data-capture feeds, log tails, and message queues.

Projects: isolated workspaces​

Everything above lives inside a project. A project is fully isolated: it has its own collections and groups, and its data is not accessible from any other project. You can create as many projects as you need, and nothing leaks between them.

Sharing and access​

You can share a project with other users at one of three access levels, each including the ones below it:

  • View: read the project's data and definitions.
  • Development: create, modify, and run publishers, transformers, and subscribers (includes View).
  • Admin: manage who has access to the project (includes Development).
