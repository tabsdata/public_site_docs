Lineage

Lineage records, for every table version, the function run that wrote it, the function code that run executed, the table versions it read, and the execution plan the run was part of. Tabsdata records lineage as part of every execution plan.

How lineage is recorded​

Traditionally, lineage is pieced together after the fact, either by parsing the queries each tool in a pipeline runs or by instrumenting each tool to report what it read and wrote. The result is only as complete as that parsing or instrumentation.

Tabsdata does not need to piece lineage together. Functions read from and write to Tabsdata tables rather than passing data directly to other functions, and each function declares the tables it uses in its decorator. A publisher declares the tables it writes with output_tables. A transformer declares the tables it reads with input_tables and the tables it writes with output_tables. A subscriber declares the tables it reads with input_tables.

Because every read and write goes through a declared table, each execution plan records exactly which table versions a function run read and which table versions it wrote, along with the function code it ran. A table version can then be traced back to the function run that wrote it, from that run to the table versions it read, and so on upstream to the publisher that read the data from an external system.

Table versions are immutable, so the lineage of a table version does not change once the table version is committed. A table version written last month still traces back to the exact upstream table versions it was computed from, even after newer versions of those tables have been written.

Table history​

Every successful function run that returns data creates a new table version that sits alongside all previous versions of the table. Each table version stores its data, row count, creation time, and the function version, execution, and transaction that wrote it.

Table version history is also available to functions. An input table written as customers@HEAD^ reads the version before the latest, and customers@HEAD~2..HEAD reads a range of versions ending at the latest.

Schema history​

Each table version carries its own schema, so a table's version history also records how its schema changed. Comparing a table version's schema with the version before it shows which columns were added, removed, or retyped.

The lineage of a table version that changed the schema shows the function run that wrote the new schema.

Function history​

Functions have a version history of their own. Updating a function creates a new function version and keeps the earlier ones, each with the code it was registered with. Every table version records the function version that wrote it, so a change in a table's data can be traced back to the code that produced it.

Viewing lineage​

In the Tabsdata User Interface, lineage can be viewed from tables, execution plans, and functions.

Tables​

Opening a table shows three tabs: Schema, Lineage, and Sample. The Lineage tab shows a graph of the execution plan that wrote the selected table version, from the external systems the data was published from, through the functions and tables in between, to the external systems it was written out to. Selecting an older table version in the table's version history shows the lineage of that table version.

Execution plans​

The Executions page shows a graph of each execution plan, which can be switched between the Execution, Lineage, and Data views. In the Execution and Lineage views, each table that feeds a function lists the data versions that function read, and each data version links to that version of the table.

Functions and table versions​

Lineage also works downstream. For a table version or a function version, the UI lists every execution plan where that version was used, so a bad batch of data or a faulty function version can be traced to each execution plan that used it.
