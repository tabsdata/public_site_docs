Merging into SQL destinations

A merge applies a batch of inserts, updates, and deletes to a destination table. Each row identifies the record it belongs to and the operation to perform on that record.

Tabsdata supports merge writes through Subscriber Functions using the Snowflake, BigQuery, and Databricks connectors. Users define how rows match and where the operation is recorded. Tabsdata prepares the batch and executes the merge in the destination system.

Merge configuration​

Set if_table_exists="merge" on the destination and provide a merge_cfg list. Each entry in the list is a MergeCfg that defines the matching keys and operation column for one destination table.

from tabsdatak.api import subscriber, TableFrameSpec
from tabsdatak.conn.snowflake import MergeCfg, SnowflakeDest


@subscriber(
    destination=SnowflakeDest(
        tables=["ORDERS"],
        if_table_exists="merge",
        merge_cfg=[MergeCfg(on=["order_id"], op_column="op")],
        schema_evolution="update",
        dest_cfg={"snowflake.schema_evolution_engine": "iceberg"},
    ),
    input_tables=["capture/order_changes"],
)
def load_orders(changes: TableFrameSpec) -> TableFrameSpec:
    return changes

In this example, order_id identifies the destination record and op identifies the operation. The Function returns the changes from the capture/order_changes Table, and Tabsdata applies them to ORDERS in Snowflake.

merge_cfg must contain one entry for each table in tables, in the same order. A single table still requires a one-entry list. merge_cfg and if_table_exists="merge" must be configured together.

MergeCfg.on must contain at least one key column. All key columns must be present in the incoming data and available in the destination when the merge runs. For a composite key, all columns must match for a row to identify an existing record.

Import MergeCfg from the same connector module as the destination. Snowflake and BigQuery also require the Iceberg schema evolution setting shown under Schema evolution.

Row operations​

The column named by op_column determines what happens to each row:

MarkerOperation
iInsert the row if its key does not exist in the destination.
uUpdate the row matching its key.
dDelete the row matching its key.

An insert does not update an existing record. An update or delete does not insert a missing record.

Markers are case-insensitive, so I, U, and D are also accepted. Whitespace is not removed: " d " is not a valid delete marker. Rows with an invalid or null marker are removed before the batch is processed.

The operation column controls the write. Tabsdata excludes it when creating or evolving the destination schema.

Multiple changes to one record​

A batch can contain several changes to the same key. Tabsdata reduces those changes to one operation per key before running the merge, using their order in the materialized batch. The order of changes in the returned data therefore matters.

The first and last valid operations determine the result:

First operationLast operationResult
InsertInsert or updateInsert using the latest row.
InsertDeleteNo destination write for this key.
Update or deleteInsert or updateUpdate using the latest row.
Update or deleteDeleteDelete the matching record.

For example, i → u → d → i becomes an insert. The record is new at the start of the batch and exists at the end. i → u → d produces no destination write because the record was created and deleted within the same batch.

For a delete, Tabsdata retains the last non-delete row as the record's payload. If every operation is a delete, it retains the first row. This allows feeds whose delete records contain only keys to be processed.

A merge preserves the batch's final effect on the destination. It does not preserve every intermediate change as a separate history record.

Destination tables and columns​

These three merge connectors can create a missing destination table from the staged data's schema, excluding the operation column. The destination database, schema or dataset, and required permissions must already be configured.

Snowflake and BigQuery build an explicit list of columns shared by the incoming data and the destination. Updates write shared non-key columns; inserts write shared columns including the keys. A destination-only column is left unchanged on an update and omitted from the insert statement, where the destination's default and constraint rules apply.

Under schema_evolution="strict", extra incoming columns are not added to an existing Snowflake or BigQuery table and are excluded from its write list. This does not make incompatible values or types valid: the destination can still reject the write.

Databricks uses Delta's wildcard merge rules. Under strict, it uses UPDATE SET * and INSERT *; under update, it uses schema evolution with the operation column excluded. Its column matching therefore follows Delta's rules rather than the explicit shared-column list used by Snowflake and BigQuery. Keep the operation marker separate from destination data columns.

Schema evolution​

Schema evolution determines whether Tabsdata can change an existing destination table to accommodate incoming data. All three destinations default to schema_evolution="strict" in Tabsdata 2.1.0.

SettingBehavior
"strict"Does not add or widen data columns on an existing table. A configured watermark column is an exception.
"update"Allows new data columns and supported type widening.

Snowflake and BigQuery require the connector's Iceberg schema evolution engine for merge mode, including when schema_evolution="strict":

# SnowflakeDest
dest_cfg={"snowflake.schema_evolution_engine": "iceberg"}

# BigQueryDest
dest_cfg={"bigquery.schema_evolution_engine": "iceberg"}

The Iceberg engine compares schemas and applies supported changes through ALTER TABLE when schema_evolution="update". It does not convert the destination into an Apache Iceberg table.

Databricks uses MERGE WITH SCHEMA EVOLUTION when schema_evolution="update". It does not use a schema_evolution_engine configuration key. Tabsdata also sets the target's delta.enableTypeWidening property to true for update and false for strict on each merge.

Type widening​

Type widening allows a destination column to hold a broader range of incoming values. The changes available depend on the destination:

DestinationSupported widening
SnowflakeWider VARCHAR lengths and greater NUMBER precision at the same scale. The connector does not widen between different base types.
BigQuerySupported numeric promotions, including INT64 → NUMERIC → BIGNUMERIC → FLOAT64, and wider type parameters.
DatabricksType changes supported by Delta type widening.

A type change outside the connector or destination's supported rules can fail the write. update does not permit arbitrary conversions.

Retrying a write​

A watermark column records the Tabsdata Transaction ID on rows written to the destination. Before writing, Tabsdata checks whether the destination contains that same ID. If it does, Tabsdata skips the write to that table.

Set watermark_column on the destination to enable this check:

SnowflakeDest(
    tables=["ORDERS"],
    if_table_exists="merge",
    merge_cfg=[MergeCfg(on=["order_id"], op_column="op")],
    watermark_column="wm",
    dest_cfg={"snowflake.schema_evolution_engine": "iceberg"},
)

Watermarks are supported with append and merge. They are rejected with replace.

The same watermark column name applies to every table listed in the destination. Tabsdata adds the column if necessary, even under schema_evolution="strict". Existing rows retain NULL; newly inserted or updated rows receive the current Transaction ID. The name must not match a merge key or the operation column, including after the destination's case handling is applied.

This check identifies a retry of the same Transaction. A later Transaction has a different ID and writes normally. The check depends on a matching ID remaining in the destination; a delete-only batch does not leave a newly stamped row.

For Snowflake, on=["order_id"] matches a stored ORDER_ID column. For BigQuery and Databricks, quoting a column name does not make matching case-sensitive. BigQuery destination table names must be enclosed in backticks, for example tables=["`orders`"].

Configuration and runtime errors​

Tabsdata validates the configuration before a write and checks the incoming batch during execution.

ConditionResult
Merge mode without merge_cfg, or merge_cfg without merge modeConfiguration error.
A bare MergeCfg instead of a list, or a list length that differs from tablesConfiguration error.
Empty on, or an operation column that matches a keyConfiguration error.
Snowflake or BigQuery merge without the required Iceberg engine settingConfiguration error.
A watermark with replace, or a watermark name that matches a key or operation columnConfiguration error.
Missing operation or key columns in the incoming batchRuntime error.
No shared data columns between the batch and destinationRuntime error.
Ambiguous incoming names when resolving a configured columnRuntime error.

For field definitions, see the MergeCfg API reference for Snowflake, BigQuery, and Databricks.
