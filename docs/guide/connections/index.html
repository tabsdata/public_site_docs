Connections

In Tabsdata, a connection describes an external system (a database, a cloud bucket, a message topic) and how to authenticate to it. A connection is not declared on your publisher or subscriber code; it is attached to a collection, and every function in that collection reads or writes through it.

This page explains how to build a connection, how the secret syntax works, and how to create the source and destination collections that carry connections.

note

This page is a work in progress and will be expanded.

Source and destination collections​

A collection belongs to a group that fixes its role:

  • sources: holds publishers that bring data in. Created with a source connection.
  • destinations: holds subscribers that send data out. Created with a destination connection.
  • default: holds transformers that turn tables into tables. No connection.

So a source or destination collection is always created together with its connection file (--conn-file); a plain collection is not.

The workflow​

  1. Find the connection type for your system: tdk connection types.
  2. Generate a fill-in template: tdk connection template.
  3. Fill in the values and secrets.
  4. Check it: tdk connection validate.
  5. Create the collection with the connection: tdk collection create --conn-file.

Steps 1–4 are offline: they don't need a running server. Only step 5 talks to the server.

Find the connection type​

tdk connection types

Type names read <system>-<access>-<direction>, so the direction is part of the name: for example mysql-sql-in (a MySQL source), s3-file-out (an S3 destination), postgres-cdc (a PostgreSQL stream source).

Get a template​

tdk connection template --type mysql-sql-in --file conn-mysql.yaml

Omit --file to print to the screen. The template lists every field: required fields as fill-ins, optional fields commented out with their default. For mysql-sql-in it looks like this:

# Connection template for: mysql-sql-in (src)
# In a string-or-secret field, a plain value uses the 'str:' prefix and a secret
# value the 'secret:' prefix (or '$secret:<ENV_VAR>' to read the value from an
# environment variable).
# A '$secret:' value is resolved on the client when the source or destination is
# created or updated with this connection.
kind: connectionDef
apiVersion: '1.0'
type: tabsdatak.conn.mysql:MySQLSrcConn
spec:

  # accepts: str:<value> | secret:<value>
  # replace <value> with the actual uri
  #
  uri: 'str:<value> or secret:<value>'
  credentials:
    kind: userPasswordCredentials
    apiVersion: '1.0'
    type: tabsdatak.conn.common.types:UserPassword
    spec:

      # replace <value> with the actual user
      #
      user: 'secret:<value>'

      # replace <value> with the actual password
      #
      password: 'secret:<value>'
  # entity_whitelist  (optional, default: none) -- a list
  # entity_whitelist: []
  # conn_cfg  (optional, default: none) -- a dict (str-keyed)
  # conn_cfg: {}

The document​

Every connection is one connectionDef document with four parts:

  • kind: connectionDef: always the same value.
  • apiVersion: '1.0': the document version.
  • type: the connector class, as <module>:<Class> (for example tabsdatak.conn.mysql:MySQLSrcConn). The template fills this in.
  • spec: the fields for this connector, its address, credentials, and any options. This is the part you fill in.

Which fields go under spec is connector-specific. See each connector's guide.

Fill in values and secrets​

Each value under spec carries a small prefix that says what it is:

FormMeaningWhere the value ends up
str:<value>a plain valuestays in the stored connection
secret:<value>a literal secret valueextracted into the secret store
$secret:<ENV>a secret read from environment variable ENVextracted into the secret store
  • Secret-only fields: passwords, access keys, tokens. They accept secret:<value> or $secret:<ENV> only.
  • String-or-secret fields: a URI, a bucket, a region. They accept all three forms: str:<value> keeps the value in the connection file; secret: or $secret: stores it as a secret instead.

When and where $secret:<ENV> is resolved. It is resolved once, at the moment you run tdk collection create --conn-file or tdk collection update --conn-file. The value is read from the environment variable ENV in the shell where you run that tdk command: your own machine, not the server. So ENV must be exported in that shell at that moment.

The resolved value is then extracted and stored as a secret like any other; the environment variable is not consulted again afterwards: not on later runs of the function, and not on the server.

For example, set the variables in the same shell, then create the collection:

export MYSQL_USER="reader"
export MYSQL_PASSWORD="s3cr3t"

tdk collection create --name world --group sources --conn-file conn-mysql.yaml

with the connection file referencing them:

      user: '$secret:MYSQL_USER'
      password: '$secret:MYSQL_PASSWORD'

The literal user and password never appear in conn-mysql.yaml. The names MYSQL_USER / MYSQL_PASSWORD are not stored anywhere either. Only their resolved values are stored, as secrets.

tip

A few fields are defined to take a plain value written directly, without a str: prefix (MySQL's uri is one). The connector's own guide shows the exact form; if tdk connection validate rejects a str:-prefixed value, write it plain instead.

How secrets are handled​

When you create or update a collection with a connection file, the client:

  1. resolves every $secret:<ENV> reference from the environment;
  2. validates the document against the connector's schema;
  3. dehydrates it: every secret value is stripped out into a separate secret payload, and the stored document keeps only a :secret: marker in its place.

The server then stores the secret values separately from the connection document. The stored document never contains a secret value, and reads never return one. tdk collection connection shows only the secret names.

Validate​

tdk connection validate --file conn-mysql.yaml

This resolves any $secret:<ENV> references (and tells you which environment variables it read), then checks the document against the connector's schema. It does not need a server.

Create the collection​

Create the collection in the matching group, passing the connection file:

tdk collection create --name world --group sources --conn-file conn-mysql.yaml
  • --conn-file is required for a source or destination collection.
  • The group is implied by the connection's direction. If you pass --group, it must match: a mysql-sql-in connection makes a sources collection.
  • A plain collection takes no connection: tdk collection create --name dataprod --group default.

Viewing a connection​

tdk collection connection --name world

Shows the connection's type and the names of its secrets and variables, never the values.

Updating a connection and rotating secrets​

Replace a collection's connection (a new address, or rotated credentials) by passing a new file to update:

tdk collection update --name world --conn-file conn-mysql.yaml

The new file is validated and dehydrated exactly as on create, and its secrets replace the stored ones.

Command reference​

CommandWhat it doesNeeds a server
tdk connection typesList the connection types installed connectors provide.no
tdk connection template --type T --file FWrite a fill-in template for type T.no
tdk connection validate --file FValidate a connection document.no
tdk collection create --group G --conn-file FCreate a collection with a connection.yes
tdk collection update --conn-file FReplace a collection's connection / rotate secrets.yes
tdk collection connection --name NShow a collection's connection (names only).yes

Every command has -h for its full options. For the rest of the tdk surface, see the CLI Guide.
