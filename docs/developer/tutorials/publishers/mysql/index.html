Publish data from MySQL

First

Create a Collection

note

The MySQL connector needs a database driver that Tabsdata cannot redistribute. See Installing Third-Party Database Drivers for how to declare it during installation.

The MySQL connector lets a publisher read data out of a MySQL or MariaDB database and land it in Tabsdata as versioned tables. You give it one or more SELECT queries; each query produces one output table.

Connector Setup​

A Functioning connector requires:

  • A YAML connection template
  • A collection
  • A publisher function python file
tip

Use the interactive component below to walk through the steps for Configuring your Connection Template, Creating a Collection, Configuring a Publisher, and Triggering the publisher

→→→

A connection template is a YAML file that defines the credentials and parameters for connecting to MySQL

Step 1aGenerate a Connection Template using the CLI
tdk connection template --type mysql-sql-in --file conn-mysql.yaml
↓

File is generated in your working directory

conn-mysql.yaml
kind: connectionDef
apiVersion: '1.0'
type: tabsdatak.conn.mysql:MySQLSrcConn
spec:
  uri: 'mysql://db.internal:3306/world'
  credentials:
    kind: userPasswordCredentials
    apiVersion: '1.0'
    type: tabsdatak.conn.common.types:UserPassword
    spec:
      user: '$secret:MYSQL_USER'
      password: '$secret:MYSQL_PASSWORD'
↓

(Optional) Validate Connection after modifying

Step 1bValidate the filled-in template (optional)
tdk connection validate --file conn-mysql.yaml

$secret:MYSQL_USER reads the MYSQL_USER environment variable in the shell where you run the CLI, at the moment the collection is created or updated. The value travels to the server in a separate secret payload; it never lives in this file. See Connections for the other secret stores.

To point the same publisher at a different database, for example dev vs. prod, change only the connection. Register the function into another source collection whose connection has a different uri; the code stays untouched.

Configuring the publisher​

tip

Click a field to expand its details and highlight where it sits in the file; type your own values to build a file you can copy straight out. Toggle optional fields to add or remove them:

function.py
from tabsdatak.api import publisher, TableFrameSpec, TrxCtx
from tabsdatak.conn.mysql import MySQLSrc
import tabsdatak.api.tableframe as tdf


@publisher(
  source=MySQLSrc(
        queries=[
            "SELECT * FROM employees WHERE emp_no > :emp_no ORDER BY emp_no LIMIT 1000",
      ],
    ),
  output_tables=["employees"],
)
def read_employees(employees: TableFrameSpec, ctx: TrxCtx) -> tuple[TableFrameSpec]:
  if employees is not None:
      emp_no = employees.select(tdf.col("emp_no").max()).one()["emp_no"]
      ctx.set_attr("emp_no", emp_no)
  return (employees,)

Configuring Triggers​

A trigger_by argument can be passed into the Publisher if you want the publisher to automatically fire on the certain conditions:

Runs on a schedule

Use CronTrigger when the publisher should poll MySQL on a fixed UTC schedule. The cron mask is standard 5-field crontab syntax, and you can optionally add start and end bounds for a limited run window.

This is the right fit when MySQL is the system of record and you want Tabsdata to check it hourly, every night, or on another predictable cadence.

read_employees.pyCron
from tabsdatak.api import publisher, TableFrameSpec, CronTrigger
from tabsdatak.conn.mysql import MySQLSrc


@publisher(
    source=MySQLSrc(
        queries=["SELECT * FROM employees"],
    ),
    output_tables=["employees"],
    trigger_by=CronTrigger("0 * * * *"),
)
def read_employees(
    employees: TableFrameSpec,
) -> tuple[TableFrameSpec]:
    return (employees,)

Reading incrementally​

Instead of re-reading a whole table every run, you can page through it, as shown in the example above. How it works:

  • The :emp_no bind takes its value from initial_values on the first run, and from ctx on every run after that.
  • After reading a batch, store the highest emp_no you saw with ctx.set_attr("emp_no", ...). Values set on ctx are persisted and become the same-named bind's value on the next run, so each trigger continues past the last row read.
  • When the query returns no new rows the slot arrives as None. Returning (None,) keeps the table's current version and leaves the watermark untouched. See None, and "no new version".

A few practicalities:

  • Compare with a strict > against a unique, monotonically increasing column (an auto-increment key, a commit timestamp), and pair it with ORDER BY + LIMIT so each run reads one bounded, ordered page. With >= the last row of one run is re-read by the next.
  • Queries can use any number of named binds; seed each one in initial_values and advance whichever ones you set on ctx.

None, and "no new version"​

A query that matches no rows fills its slot with None, not an empty table. A publisher that returns None for a table tells Tabsdata "no new version, keep the previous one as current":

@publisher(
    source=MySQLSrc(queries=["SELECT * FROM city WHERE 1 = 0"]),
    output_tables=["city"],
)
def read_when_available(city: TableFrameSpec) -> tuple[TableFrameSpec]:
    return (city,)

Troubleshooting​

  • Access denied / authentication errors: $secret: references were resolved from your shell when the collection was created, so check what those variables held at that moment (re-run tdk connection validate --file conn-mysql.yaml to see what resolves now), and that the database user has SELECT on every table the queries touch.
  • Connection timeouts: the uri host must be reachable from the Tabsdata server, not from your machine. Driver-level settings (timeouts, charset) go in the connection's conn_cfg.
  • One query fails: the whole run fails and nothing is published. With transactional=True (the default) all queries share one transaction, so a partial set of tables never lands.
  • A run succeeds but a table has no new version: its query matched no rows and the function returned None for that slot, which means keep the current version. See None, and "no new version".

Streaming changes instead​

MySQL also offers a stream source, MySQLCdcStreamSrc, with its own connection type mysql-cdc. It streams every insert, update, and delete from the binlog rather than re-running a query. See MySQL CDC.
