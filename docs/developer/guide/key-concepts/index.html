System architecture​

Tabsdata is a distributed, horizontally scalable system that runs on a Kubernetes cluster. It keeps three things separate: the functions that process data, the user data itself, and the system state and metadata. It also uses the same binary everywhere, so the Tabsdata you run in production is the exact one you run on a laptop for development.

Functions and execution​

Publishers, transformers, and subscribers are Python functions that work with data through the TableFrame API, built on Polars.

  • Every function runs isolated from the others, so one cannot interfere with another.
  • Processing runs in streaming mode, so a function can handle data larger than the available memory.

Data storage​

User data is stored in cloud storage or a file system, and can be spread across several providers at once: Amazon S3, Azure Blob Storage, Google Cloud Storage, or a network file system. Internally, Tabsdata stores table data as Parquet files.

State and metadata​

A database holds all of Tabsdata's state. This includes every piece of system and user metadata: projects, collections, functions, table versions, execution plans, permissions, and more. The user data itself lives in storage, never in the database.

Connectors​

Tabsdata reaches external systems through connectors. They are plug and play: new connectors are added through a simple mechanism, with no change to the core.

Security​

  • Authorization is RBAC-based (role-based access control). A simple permission model is exposed by default. See Permissions for the access levels.
  • All credentials live in a credentials store: both Tabsdata's own credentials and the credentials for your connections to external systems.
note

Even when you provide a credential inline, Tabsdata extracts it into the credentials store. Credentials are never stored in the clear.

Deployment​

Tabsdata runs on:

  • Linux: for production.
  • macOS and Windows: for development.

For development, Tabsdata ships a lightweight, embedded version of Kubernetes that runs pods as native processes on your own computer. It needs no root or admin access to set up or run. Because the same binary runs in development and production, what you build locally behaves the same once deployed.

AI integration​

Tabsdata was designed from the ground up to integrate with AI. The integration is built from three parts:

  • The Tabsdata MCP server, which exposes Tabsdata to AI agents.
  • A skills library and a vector database, which give agents the knowledge and context they need to work with your data.

There are two ways to use it:

  • A built-in agent handles operational tasks inside Tabsdata.
  • Your own coding agents (Claude, Gemini, Codex) connect through the MCP server.

The authorization model is fully integrated with the MCP server. When an agent acts on your behalf, it can do exactly what you are authorized to do, and nothing more.
