Secrets Management

Credentials live on a Connection, never in a Function. A Function names the system it reads or writes and nothing else, so the same code runs against a different account by changing the Connection it sits behind.

How a credential reaches the server​

A credential field in a Connection document takes one of two forms:

FormMeaning
secret:<value>the value itself, written in the document
$secret:<VARIABLE>read from the environment variable named VARIABLE

Both end up in the same place. Before the document is sent, Tabsdata resolves every $secret: reference into its value, validates the document, then dehydrates it: the credential values are stripped into a separate payload and each credential field is replaced with the marker :secret:. The server stores the dehydrated document and the values go to its secret store.

So the stored Connection never holds a credential, and nothing reads the environment variable again afterwards. $secret: is an input form, not a live reference.

note

Stored values cannot be read back. A Connection can list the names of its secrets and never their values, which is also why rotating a credential means updating the Connection rather than changing anything outside it.

Where $secret: is resolved​

The variable is read from the environment of whichever process resolves the document, and that is not always your shell:

Creating the Connection withReads the variable from
tdk collection create --conn-filethe shell you run tdk in
an AI agent over MCPthe server's agent process

A variable exported in your own terminal therefore does not reach an agent working over MCP. Making it reach one means putting it in the server's environment, which has three costs worth knowing before you try: the instance has to be restarted for every credential change, it only works on kminus rather than EKS, and every Function on that server can read the environment, including the agent itself.

Choosing an approach​

Ordered from most to least protective:

  1. Create the Connection yourself, with tdk collection create --conn-file, then let an agent register Functions against the Collection. The agent never sees a credential, because by then there is nothing to see: the values are already in the secret store.
  2. Ask an agent for the connection template, fill in the credentials yourself, and run the create yourself. Same outcome, less typing.
  3. Give an agent the credentials and let it create the Connection. Simplest, and the values pass through the agent's context, which means they are written to its session transcript on disk.

Putting the credentials in a file and pointing an agent at the path is option 3, not option 1. The file keeps them off your screen; the agent still reads them.

warning

Whatever an agent reads, it stores. If a credential has passed through an agent session, rotate it when you are done rather than assuming the transcript is private.

Values that are not secret​

A field that accepts either kind takes a third prefix, str:<value>, which keeps the value in the stored Connection in plain text. A URI, a bucket, or a region is usually written this way; it is readable afterwards, which is what you want for something you will need to check.

Password, key and token fields do not accept str:. They are secret-only, so the value is always harvested.
